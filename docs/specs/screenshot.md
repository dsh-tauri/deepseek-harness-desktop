# 截图交付规范

用户要求截图时，先读取本规范；用户指定的数量、语言、主题与展示范围优先。截图用于展示改动，不替代测试结果。

## 1. 截图来源与范围

- 优先截取当前改动实际运行的页面或桌面窗口，先完成交互并等待目标状态就绪，再截图。
- 截图应包含足够的上下文，让读者看清入口位置、菜单顺序或操作结果；不要只截一段孤立文字。
- 使用测试数据，避免暴露真实会话、路径、账号、密钥、Token 或其他私人信息。
- 保留实际组件、样式与文案；禁止手工绘制界面、拼接效果图或修改 DOM 伪造功能结果。
- 若环境不能运行完整应用，可渲染生产组件并使用实际样式生成组件预览，但必须注明“组件预览，非完整桌面集成截图”及未验证范围。用户明确要求真实运行截图时，预览不能替代；无法完成则说明阻碍。
- 新窗口等原生功能需使用真实桌面窗口证明结果；浏览器预览只能展示菜单，不能据此宣称原生窗口创建、目标会话加载或源窗口状态保持已验证。

## 2. 环境与验证

- 复用仓库已有驱动：页面使用 Playwright 库 API，原生桌面窗口使用 WebdriverIO；遵循 [插件测试规范](./plugin.test.md) 与 [桌面测试规范](./desktop.test.md) 的隔离要求。
- 不修改用户数据、不关闭用户进程、不另起服务器冒充当前页面。先确认运行地址与产物版本对应当前改动。
- 遵守插件开发期间禁止执行 Build 的约束。截图需求不构成构建许可；已有产物不对应改动时，不将其标为当前改动的截图。
- 截图前确认目标元素可见、没有加载遮罩或意外错误，尺寸与缩放足以读清内容；保存后打开图片核对，不仅检查文件存在。
- 对用户指定的每个 PR 分别提供对应截图；更新菜单位置或文案后重新截图并原地替换旧图。

## 3. 存储与上传

- 图片与临时渲染脚本放在工作区的临时目录（如 `.temp/`），不提交到源码仓库，也不创建专门的资源分支。
- GitHub PR 使用 `github.com/user-attachments/assets/...` 附件链接，不使用本机路径或为截图新增仓库文件。优先使用现有 `gh` 登录态上传，不索取或输出凭证。
- 上传失败时说明原因，不退回提交图片到仓库；未经用户同意，不上传到第三方图床。
- PR 正文用 `![说明](附件链接)` 展示图片，并简短标明截图来源、目标状态及必要的验证限制。截图与测试结论分开写。
- 同一 PR 更新原正文，不补发重复截图评论。上传后将链接写入 PR，再检查附件可访问；未被正文或评论引用的附件可能返回 404。本机文件存在不等于远端上传成功。

已有 `gh` 登录态且仓库权限至少为 `WRITE` 时，可上传 PNG：

```bash
gh api repos/OWNER/REPO --jq .id
gh api --method POST 'https://uploads.github.com/user-attachments/assets?name=screenshot.png&content_type=image%2Fpng&repository_id=REPOSITORY_ID' -H 'Content-Type: application/octet-stream' -H 'Accept: application/vnd.github+json' --input .temp/screenshots/screenshot.png --jq .url
```

将 `OWNER/REPO` 替换为目标仓库，`REPOSITORY_ID` 替换为第一条命令返回的数字，文件名与路径替换为实际图片。图片不超过 10 MiB；真实 MIME 放在 `content_type` 参数中，文件用二进制 `--input` 发送。该端点被官方 `gh` 使用，但不是承诺稳定的公开 REST 接口，仅支持 GitHub.com 与 GitHub Enterprise Cloud，不支持 GHES；上传不可撤销，提交前先检查隐私。

## 4. 交付检查

提交 PR 前确认：图片对应最新改动、文字可读、无隐私信息、来源与限制如实标注、图片未进入 Git diff、PR 中的附件可访问。
